# MULTI AGENT CONTROL

Purpose: Source-repo governance summary for how the pony runtime should divide responsibility.
Contract: Shared policy document. It defines the intended coordination model and boundaries, but Twilight still owns live operational state and routing.

Coordinator focus for agenic-pony-system on main:
- keep the source-repo Warp launcher set dedicated to Celestia, with Twilight remaining the coordinator
- keep the source-repo Celestia launcher independent from `~/.codex/*.config.toml` files during normal startup, while treating `celestia` as the canonical manual profile name if an operator explicitly uses a Codex profile
- keep source-repo governance changes focused on launcher policy, prompt policy, coordinator policy, docs, and source-of-truth structure
- keep tactical project coordination pushed down to Twilight instead of absorbing it into Celestia governance work
- require a Git freshness preflight before explicit task execution: when an agent is on `main` and `git status --porcelain` is empty, it must run `git fetch --prune origin` then `git pull --ff-only`; dirty main worktrees, non-main branches, and non-fast-forward histories must be recorded and routed to Twilight rather than auto-pulled
- reject stale linked worktrees as implicit starting points for new assignments: Twilight must verify refreshed project `main` first, then explicitly prepare the worker branch/worktree; no reset, rebase, discard, or other rewrite of a dirty worker worktree is permitted merely to make it current
- keep external target-project installs working, especially Handshake
- require customized/source-built Codex binaries to preserve upstream-version detection without recommending `npm install -g @openai/codex`; their update notice should direct operators to update the custom source branch and rebuild, with the actual upgrade separately authorized
- require crash-safe target-project install refresh: a launcher may reclaim an ownerless install lock or one owned by a dead local PID, while never removing a lock attributed to another host
- keep target-project bootstrap/install hygiene from dirtying repos by default when generating local `pony/` runtime state
- keep that no-dirty-default policy enforced from source-layer install/bootstrap behavior, including managed Git-backed ignore policy for generated target-project `pony/` trees
- keep MCP and other Codex session credentials flowing through explicit launcher env files instead of relying on incidental shell startup state
- keep the runtime aligned with the current shared-state rule: workers report changes to Twilight, and Twilight maintains the authoritative coordination state rather than relying on worker-local file writes
- keep worker and Twilight sessions commit-capable under `workspace-write` by granting the entire shared repository Git common directory (normally `<project>/.git`) as a writable root alongside the active worktree and shared project-root pony state paths; ponies are trusted collaborators, so this is a polite coordination boundary rather than branch-level security isolation
- treat assigned worktrees and branches as the normal ownership convention, not an exclusive-access restriction: ponies may exchange code, commits, and artifacts across worktrees when coordination requires it, while destructive history rewriting and discarding another pony's dirty state still require explicit direction
- keep Celestia's August 2, 2026 source-governance lane broader than ordinary workers without using `danger-full-access`: when the generated agent roster exposes live cross-repo targets, allow Celestia's launcher to add those target project roots plus their registry/message-log runtime paths as writable roots so source-governance `/tell` and exact follow-up writes are not blocked by read-only target lanes
- keep Twilight's Celestia-delivery exception narrow: when the generated roster exposes the agenic global singleton `Princess Celestia Sol Invictus`, allow Twilight's launcher to add only that resolved Celestia `messageLogPath` as a writable root, not the rest of the target repo
- require workers to send the needed direct `/tell` messages in the same run when a coordination-relevant state change occurs; short aliases and full display names should both resolve through the active worker identity map
- keep `/tell` routing team-local by default for ambiguous targets so same-named ponies in different live teams cannot receive one another's traffic by accident
- allow explicit cross-repo `/tell` delivery only when the target is disambiguated through the active generated agent roster, such as `<project>:Twilight Sparkle`; preserve `Princess Celestia Sol Invictus` as the unique global source-governance identity
- treat unqualified `Celestia` delivery as the explicit `agenic-pony-system` source-repo governance lane by default; repo identity and governance authority are implied by the recipient, so senders do not need extra ceremony beyond stating the concrete operational purpose
- keep the generated `CODEX_AGENT_CONFIG` roster contract explicit: include `messageLogPath`, `registryPath`, qualified aliases, the local project roster, and any live cross-project targets visible on the active bus; shell helpers should invoke `agent-config.py` via `python3` when the file exists instead of relying on its executable bit
- make `CODEX_AGENT_CONFIG` the source of Pony-specific agent IPC policy: Agenic launchers must always generate and export it, every roster entry must carry an explicit `globalSingleton` boolean and `mailboxPath`, and generic Codex `agent_ipc` must rely on those fields rather than hard-coding `PRINCESS_CELESTIA_SOL_INVICTUS`, Pony mailbox layout, or other Pony identities and paths
- keep the agent IPC wire format generic: writers emit `agent_name`, `agent_symbol`, `agent_aliases`, and `from_agent_name`; Codex may retain the former `pony_*` names only as read aliases during compatibility migration, while Agenic registry readers accept both generations
- require any Twilight context acting on the agenic source-governance lane to have append access to that lane's resolved `messageLogPath`; if routing resolves correctly but append fails because of sandbox policy, record a permission blocker rather than a routing blocker
- treat simple pony-to-pony `/tell` pings, acknowledgements, and short live notes as conversational IPC by default: reply live with `/tell` unless the message also carries a durable state change, blocker, or explicit write request
- distinguish ephemeral `/tell` traffic from durable inter-project governance or enhancement requests: ephemeral traffic may use the current short-lived, per-sender-coalesced chat lane, but durable requests must persist until explicit recipient acknowledgement and must not be discarded by live-message cleanup
- recognize that the existing Codex TUI chat transport currently gives every message the ephemeral one-hour/coalesced behavior; a true durable `/tell` delivery class therefore requires a Codex TUI IPC protocol change, not merely source launcher or documentation changes
- treat mailbox files as notification lanes rather than reboot-state storage; if a fact must survive restart, require Twilight to record it in the shared authoritative coordination mechanism from an exact worker write request
- keep pending user approvals isolated from routine mailbox acknowledgements and generated helper review text; unresolved approvals belong in a dedicated coordinator approval lane until the user answers
- keep generated `Twilight review needed`-style snippets out of durable coordinator history; they belong in a review queue or todo surface, not in canonical event history
- require blockers caused by missing connection strings, secrets, endpoints, approvals, or other external prerequisites to name the exact missing artifact, the expected owner, and the next unblock step in canonical worker state before idle
- require every worker stopping point to leave behind a concise restart capsule in the assigned workfile, and when that capsule implies shared durable coordination changes, require the matching exact `/tell` update to Twilight in the same run
- keep launcher-generated system/developer prompts limited to stable boot identity and mechanics: identity and role, project/workspace, nominal branch/worktree, prompt/title/accent, assigned state-file paths, local coordination paths, `/tell`, alerts/audio, repo boundaries, safety rules, and idle behavior
- never serialize mutable worker state into an immutable/high-priority startup prompt: no current task, status enum, blocker, branch-specific handoff, implementation scope, next action, deployment instruction, or historical work summary; only pointers to those mutable sources may appear
- require every launch to use the neutral phase `ORIENTATION_REQUIRED`, never a concrete `Current condition`; after the cheap self-brief, require read-only orientation from the assigned memory capsule first when present, then the assigned workfile and Twilight-managed authoritative coordination state
- treat orientation as context gathering only: it must not begin implementation, change files, send work messages, repair preflight, deploy, or rerun; work starts only after an explicit post-start user or Twilight instruction, and historical state never becomes authorization merely because it was read
- if orientation sources conflict, require the worker to report the exact sources and conflicting values to Twilight and remain parked; launcher-cached state must not break the tie
- ensure a clean launch never automatically assigns or resumes work; task assignment belongs to the live post-start user or Twilight channel
- if the user points out a non-file-changing mistake, require the pony to correct it immediately instead of asking whether to proceed
- require workers to refresh memory capsules whenever durable restart context materially changes, not just at graceful shutdown; shutdown is the last safety pass, not the primary save point
- require useful memory capsules to capture the current task, overall direction or why, branch and worktree, specific files in play, exact next step, open problem or uncertainty if any, blocker only if one truly exists, handoff note if relevant, and a real last-updated timestamp
- when the user declares shutdown, require Twilight to fan out save-memory-and-report-status requests to the live agents before Twilight saves her own memory capsule
- implement the queue/input runtime behavior from `docs/runtime-loop.md`
- keep shell launch startup robust by invoking `start-session.sh` directly rather than typing a synthesized command into the interactive buffer
- prefer lightweight parked hosts over disposable direct Codex launches so tmux scrollback, editor history, and restart continuity survive ordinary relaunches for more than just Celestia
- retain a private rolling restart transcript of the most recent 1,000 terminal-output lines per Codex agent under the project-local runtime directory; refresh it during live output or tmux monitoring, read it only as crash-recovery context, and never treat it as durable coordinator authority
- do not treat per-worker local `pony/work/*.md` or `pony/team.coordination/*.status.md` files as shared authority in the current runtime; they are workspace artifacts unless Twilight is explicitly assigned to maintain them
- allow concise letters to Princess Celestia through `pony/team.coordination/celestia.mailbox.md` for source-repo governance or shared-system requests, while leaving day-to-day coordination with Twilight
